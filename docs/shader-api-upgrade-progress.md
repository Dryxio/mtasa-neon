## Stage 2 — Multiple scheduled scene views

- [x] Raise scene-view cap + update modes (done — the original two-view fixed cap has been removed entirely: `CreateSceneView` is bounded only by `CanCreateRenderItem`'s existing memory accounting, and `RenderRequestedSceneView` renders every view with a pending request every frame, no count limit. `dxGetRenderCapabilities().MaxSceneViewsPerFrame` now reports `-1` ("no fixed cap") rather than a specific number. Cost scales directly with how many views a script actually requests a render for - unbounded concurrent SceneViews is a real performance cost a resource author now opts into deliberately, not a ceiling the engine imposes. Debug Win32 builds, two-camera isolation and throttled-mode tests pass. `dxSetSceneViewUpdateMode` supports `manual`, `once`, `always`, `every_n_frames` and millisecond `interval`. The public output retains its last complete frame until replacement copying finishes. Resolution and pixel count do not affect scheduling.)
- [x] Isolated per-SceneView world-material shader assignments that ignore primary/other-view shader maps (done — scoped alternate matching, resource-owned shader references and apply/remove Lua entry points passed Debug builds and two-view visual isolation, restart and device-reset tests. Commit: `bda1eac90`. Target-element filtering (the plan's deferred follow-up, mirroring `engineApplyShaderToWorldTexture`'s own `targetElement`/`appendLayers`) has since been added: `SSceneViewShaderAssignment` carries an optional target entity resolved against a new `CRenderWare::GetRenderingClientEntity()` getter, with the same appendLayers exclusivity semantics as the world-texture path. The `dxApplyShaderToSceneViewWorldTexture`/`dxRemoveShaderFromSceneViewWorldTexture` development aliases mentioned in the plan have been removed now that the signatures reached parity - only the `engine*` names exist. Commit: `dd7038bee`)
- [x] SceneView output post-process chain using safe render passes and ping-pong targets; `dxGetSceneViewTexture` remains a plain getter (done for the single-effect path — a private intermediate target and explicit input binding, runtime-confirmed via `sceneview_world_shader_test`'s output-shader test (grayscale pass, one view affected, one left as a color reference). Multi-effect ordering/ping-pong chaining remains deferred, unneeded until a demo actually requires stacking more than one output shader)
- [x] Matrix-based SceneView camera setter in addition to the existing position/target setter (done — `dxSetSceneViewMatrix` and `DxSceneView:setMatrix` validate finite, non-degenerate basis vectors, normalize the camera basis and reuse the existing internal `CMatrix` path; also accepts the same 4x4 table format as `setElementMatrix` (verified to already share `ReadMatrix`, no code change needed there). Runtime-confirmed via `sceneview_world_shader_test`'s matrix-camera test: a hand-built orbiting table matrix on one view, `getElementMatrix(localPlayer)` reused directly on the other)
- [x] Orthographic SceneView projection (done — `dxSetSceneViewOrthographicProjection(sceneView, width, height, nearClip, farClip)` / `dxSetSceneViewPerspectiveProjection(sceneView)`, validated (finite, positive width/height/near/far, far > near) in the Lua binding, stored on `CClientSceneView` and consumed by a new `CMultiplayer::SetSceneViewProjection(...)` call issued immediately before each `RenderSecondaryScene()`, mirroring the existing `SetSceneViewShaderContext` scoped-per-render-context pattern. Since GTA's own camera model has no orthographic concept, `CMultiplayerSA::RenderSecondaryScene` overrides the RenderWare camera's projection directly via the real `RwCameraSetProjection`/`RwCameraSetViewWindow`/`RwCameraSetNearClipPlane`/`RwCameraSetFarClipPlane` entry points, applied unconditionally (perspective included) after GTA's own `CopyCameraMatrixToRWCam`/`CalculateDerivedValues` position the view matrix - required because every SceneView rendered this frame shares one physical RenderWare camera object sequentially (there is no per-frame view-count cap). `dxGetSceneViewInfo` reports the current mode via a new `orthographic` field. Known, documented limitation: GTA's own coarse `ConstructRenderList` visibility selection still culls against the perspective frustum (no orthographic awareness in GTA's own camera model), so an orthographic view's candidate entity list can be a superset of a tightly-fit one - RenderWare's own per-object frustum test during `RenderScene` does use the corrected projection, so this affects draw-call count, not correctness of what is drawn. Runtime-confirmed via `sceneview_world_shader_test`'s orthographic-projection test: View 1 perspective top-down for reference, View 2 orthographic from an elevated 3/4 angle (a straight top-down angle made the no-foreshortening effect too subtle to judge - an angled view where receding geometry visibly does not shrink is the actual confirming test). Debug Win32 builds pass for Game SA, Client Core, Multiplayer SA and Client Deathmatch. **Stage 2 is now closed.**)

## Stage 3 — Cubemap render targets

- [x] `CCubemapRenderTargetItem` (done — wraps an `IDirect3DCubeTexture9` plus one cached render-target surface per face and a single depth-stencil surface shared across all 6 faces, since they render sequentially, never simultaneously. Capability-gated on Stage 1's `bCubemapRenderTargetSupported`/`iMaxCubemapEdgeLength`, plus a `CheckDeviceFormat(..., D3DRTYPE_CUBETEXTURE, ...)` guard mirroring `CreateRenderTarget`'s own format validation. `CRenderItemManager::BeginCubemapFaceRender` reuses `CRenderStateScope` directly (its `ApplyRenderTargets`/`ApplyViewport` split was already designed with "one cubemap face" as a documented use case) rather than going through `BeginRenderPass`'s `CRenderTargetItem`-array API, since a cube face is a raw `IDirect3DSurface9*` with no owning 2D render-target item.)
- [x] `dxCreateCubemapRenderTarget` / camera / face-render Lua API (done — `dxCreateCubemapRenderTarget(edgeSize [, colorFormat])`, `dxSetCubemapRenderTargetCamera(cubemap, x, y, z [, nearClip, farClip])`, `dxRequestCubemapRenderTargetRender(cubemap [, { "posx", ... } ])`, `dxGetCubemapRenderTargetTexture`/`dxGetCubemapRenderTargetInfo`. A cubemap has no per-face orientation to configure - the 6 axis-aligned directions (matching `D3DCUBEMAP_FACES` index order) are what makes it a cubemap - so unlike SceneView there is no matrix/FOV setter, only a fixed probe position. Purely request-driven, no update-mode scheduling and **no per-frame render cap**: `dxRequestCubemapRenderTargetRender` with no face list requests all 6, and all 6 render the same frame they're requested (`RequestFaces`/`ClearRenderedFaces` on `CClientCubemapRenderTarget` are still split rather than one consume-and-clear call, so a face whose render pass fails to begin - eg. device not ready - stays queued for the next frame instead of being silently dropped, but nothing throttles a normal successful request). Scripts that want to spread the cost over multiple frames do so themselves by requesting a subset of faces each call - the plan's own "partial per-frame face updates for budget control" is opt-in, not enforced.
  - Reuses `RenderSecondaryScene()` (the SceneView world-render procedure) completely unchanged for the actual per-face draw, exactly as the plan specifies - `RenderSecondaryScene()` already renders into an internal scratch raster and copies the result to whatever surface is bound as render target 0 when it's called, so it was already agnostic to whether that surface belongs to a 2D `CRenderTargetItem` or one face of a cube texture.
  - Runtime-confirmed in-game via `sceneview_world_shader_test`'s `cubemap_render_target` test (all 6 faces render and unwrap correctly in the on-screen cross layout). Debug Win32 builds pass for Game SA, Client Core, Multiplayer SA and Client Deathmatch.
  - GTA's own camera model (`CalculateDerivedValues`) ties its computed frustum to whatever aspect ratio it assumes for the primary display, not a square off-screen target's actual 1:1 dimensions - the same class of problem the orthographic-projection fix above addressed for a different projection type. A new `CMultiplayer::SetSceneViewSquarePerspective(bool)` call, consumed the same scoped-per-render-context way as `SetSceneViewProjection`, forces the view window to an exactly symmetric `(tan(45), tan(45))` frustum after `CameraCalculateDerived` runs - the only configuration where a 90-degree FOV is genuinely 90 degrees on both axes - and also applies `SetSceneViewProjection`'s near/far pair (previously meaningful only for orthographic mode) so a probe's clip range doesn't depend on whatever the primary camera's happened to be.
  - Face-to-world-direction mapping is a **new, self-contained convention**, not an attempt to match an external "D3D-native" cubemap orientation: `CClientRenderElementManager::RenderRequestedCubemaps` points the camera along GTA's own world-space basis vectors per face (index 0-5 = +X/-X/+Y/-Y/+Z/-Z, matching the same index order `GetCubeMapSurface` was called with when each face's surface was cached), and since `texCUBE`'s hardware face-selection is driven purely by the dominant axis of the lookup vector, any code that later samples the cubemap with a direction expressed in that same GTA world-space basis is automatically consistent with what was rendered - there is no separate "did I match D3D's convention" risk for *which* face shows *which* direction. The one narrower risk this doesn't automatically rule out is in-face rotation/mirroring (getting the two minor axes' image-space orientation backwards within a correctly-selected face) - visually diagnosable, not a wrong-face bug. The `cubemap_render_target` test unwraps all 6 faces into the standard on-screen cross layout via a small `texCUBE`-sampling preview shader specifically to let this be checked visually, and runtime testing confirmed all 6 faces render and unwrap correctly.)

## Stage 4 — Shadow-mapping primitives

- [ ] 4.0 Perspective SceneView target-aspect correction (derive projection from the existing `dxCreateSceneView(width, height, ...)` dimensions, with an optional explicit aspect override; no redundant resize API) (pending)
- [x] 4.1 Shadow-map camera (done via the **encoded-depth** path; native sampleable Z-buffer depth for SceneViews is architecturally blocked, explained below)
  - **Native path attempted and confirmed non-viable.** `dxCreateSceneView` briefly gained a trailing `sampleableDepth` parameter, wired through a sampleable `CDepthStencilTargetItem` (base class changed `CRenderItem`→`CTextureItem`, mirroring `CCubemapRenderTargetItem`, so its `IDirect3DTexture9` works with `CShaderItem::SetValue(name, CTextureItem*)` for free) and a new `dxSetShaderDepthTextureValue(shader, name, sceneView)` (kept separate from `dxSetShaderValue`, which already has an established, documented meaning for a `sceneView` argument - bind its COLOR output). In-game testing showed a solid black depth texture. Root cause: a SceneView's off-screen world render goes through a private, persistent RenderWare camera (`m_pSecondarySceneCamera` in `CMultiplayerSA.cpp`) whose `bufferDepth` is an RW-owned raster; `RwCameraBeginUpdate` unconditionally rebinds the device's depth-stencil surface to that raster's own plain `D3DFMT_D24S8` surface, confirmed via `pDevice->GetDepthStencilSurface()` immediately after `RwCameraBeginUpdate` returning a surface different from whatever `BeginSceneViewRender` had bound beforehand - so the sampleable INTZ/DF24/DF16/RAWZ surface never received any real depth data. A `StretchRect`-based copy (mirroring exactly how the color output is already bridged the same way) was attempted next, but failed in-game with `D3DERR_INVALIDCALL`: a diagnostic dump confirmed source=`D3DFMT_D24S8` and destination=`INTZ`, both correctly sized and `D3DUSAGE_DEPTHSTENCIL`, different surfaces - D3D9 requires **matching formats** for depth-stencil `StretchRect` copies (unlike color, which allows conversion), so this is a hard API restriction, not a fixable parameter. Two follow-up research passes (contrasting this against MTA's existing primary-scene `DepthBuffer` shader feature, `CRenderItemManager::SaveReadableDepthBuffer`) confirmed *why* the primary camera doesn't hit this: it has no private off-screen Z-buffer raster of its own (tied to the back buffer instead), so a plain `SetDepthStencilSurface` swap around the whole primary frame just sticks - an off-screen `RWRASTERTYPEZBUFFER`-raster camera has no way to skip RW's unconditional rebind. Making RW's own Z-buffer raster INTZ-backed directly (so the world render writes real depth natively) would require reverse-engineering RenderWare's private per-platform raster extension struct layout, with no existing precedent anywhere in this codebase and real crash risk if a struct offset is wrong - rejected as disproportionate for this feature. **Result:** `dxCreateSceneView`'s `sampleableDepth` parameter now explicitly rejects `true` with a clear error (`Not supported`) instead of silently creating an item that could never receive real depth data - matching the plan's "explicit failure over silent degradation" rule. The depth `StretchRect` attempt, its diagnostic dump, and the associated `CDepthStencilTargetItem`/`CClientDepthStencilTarget` base-class changes remain in place and still work correctly for their original, unaffected use case: standalone `dxCreateDepthStencilTarget`'s sampleable path used with `dxBeginRenderPass`/`dxCreateMrtSet`, which bind the D3D9 device directly and never go through RenderWare's world-render camera at all. `dxSetShaderDepthTextureValue` remains available for that path. In the same pass, fixed a latent bug the base-class change had introduced: `CDepthStencilTargetItem` had redeclared its own `m_uiSizeX`/`m_uiSizeY`, shadowing the identically-named members it now inherits from `CMaterialItem` - `CShaderItem::SetValue`'s first-declared-texture size mirroring reads through a `CTextureItem*`, which resolved to the inherited (always-zero) copy, not the one `PostConstruct` actually set. Removed the redeclaration so both refer to the same inherited members.
  - **Encoded-depth path implemented instead**, matching the plan's own documented fallback for when native sampleable depth isn't available. New `shaders/depth_encode.fx` in `sceneview_world_shader_test` replaces the full vertex+pixel draw for every object it applies to, outputting distance-to-camera as grayscale color instead of the object's normal texture/lighting - it uses the `WorldView`/`WorldViewProjection` matrices MTA's existing automatic-shader-value system (`CEffectParameters::ReadCommonHandles`) already fills in by variable name (`WorldView` rather than the projected `WorldViewProjection`, since clip-space W only tracks view-space depth under perspective and is always 1 for an orthographic camera). Applied to a SceneView globally via `engineApplyShaderToSceneViewWorldTexture(shader, sceneView, "*")` - Stage 2's existing per-view world-shader isolation, unchanged - so the SceneView's own ordinary color output becomes the depth-encoded "shadow map" once the shader is applied; no C++ changes were needed for this path at all. Directional-light orthographic projection reuses Stage 2's `dxSetSceneViewOrthographicProjection` entirely, no new camera code. `getSunDirection()` (`Client/mods/deathmatch/logic/luadefs/CLuaWorldDefs.cpp`, reading `CTimeCycle::m_vecDirnLightToSun` via a new `CMultiplayer::GetSunDirection`) positions the shadow camera along the live sun direction. Known limitation, not yet resolved: color-write suppression during a "depth-only" pass was not implemented - `D3DRS_COLORWRITEENABLE` is not one of the states RenderWare's own fixed-function cache tracks (per `CRenderStateScope`'s `DefinedState()`), so toggling it directly risks the same class of RW/D3D9 state-cache desync this session's very first fix (`RwD3D9SetTransform`) was about; not applicable to the encoded-depth path either way, since it replaces the whole draw rather than relying on the fixed-function Z-buffer.
  - Exercised via `sceneview_world_shader_test`'s `shadow_map_camera` test: two SceneViews share a directional-light orthographic camera positioned along the live sun direction; View 2 has `shaders/depth_encode.fx` applied via the wildcard `"*"` match, View 1 stays unmodified for comparison. Debug Win32 builds pass for Game SA, Client Core, Multiplayer SA and Client Deathmatch; **not yet confirmed in-game**.
